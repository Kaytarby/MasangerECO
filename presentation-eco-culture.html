Личные и групповые чаты

Direct-чат нельзя создать дважды — сервер найдёт существующий SQL-запросом с двумя JOIN. Группа создаётся чекбоксами с дедупликацией участников через Set: создатель никогда не добавится дважды.

🔑 Сокет без токена не пройдёт

io.use() проверяет JWT из handshake.auth.token до подключения. Нет токена или подпись битая — Authentication error, соединение не состоится.

🚪 Комнаты на любой случай

При подключении пользователь автоматически входит во все свои chat_* комнаты (один SQL-запрос) плюс персональную user_* — задел для личных уведомлений. Открытие нового чата — событие join_chat.

🧹 Чистый жизненный цикл

SocketProvider создаёт сокет только при наличии токена и пользователя, а при выходе — socket.close(). Слушатель new_message снимается через socket.off при размонтировании. Никаких утечек.

База данных · SQLite, файл eco_culture.db

4 таблицы. 2 индекса.
И одна умная миграция.

Схема создаётся автоматически при первом запуске (CREATE TABLE IF NOT EXISTS). Включён WAL-режим — чтение не блокирует запись. Старым базам без last_read_at колонка добавится сама через PRAGMA table_info + ALTER TABLE.

👤 users

id PK · phone UNIQUE NOT NULL · password NOT NULL (bcrypt-хеш) · name NOT NULL · bio · avatar · created_at

Телефон — уникальный логин. Пароль в открытом виде не существует нигде.

💬 chats

id PK · type NOT NULL ('direct'|'group') · name · avatar · created_at

У direct-чатов имя и аватар подставляются из профиля собеседника на лету.

🤝 chat_participants

chat_id · user_id · last_read_at · UNIQUE(chat_id, user_id)

Сердце системы непрочитанных: один timestamp вместо флага на каждое сообщение.

✉️ messages

id PK · chat_id NOT NULL · sender_id NOT NULL · text · image_url · created_at

Текст и фото — в одной записи: фотография с подписью работает из коробки.

🚀 Индексы, которые реально работают

idx_messages_chat (chat_id, id) — история чата и «последнее сообщение» находятся одним проходом по индексу; сортировка списка чатов — по MAX(id) последнего сообщения, а не по строкам дат. idx_participants_user (user_id) — все чаты пользователя при подключении сокета одним запросом.

🧮 Как считаются непрочитанные

Один SQL-запрос на весь список чатов: для каждого чата — COUNT(*) сообщений, где отправитель не вы и created_at > last_read_at (или отметки чтения ещё не было). Ответили в чате — ваш last_read_at обновился автоматически: нельзя «не прочитать» то, на что ответил.

server.ts · схема базы (фрагмент дословно)
const db = new Database(process.env.DB_PATH || 'eco_culture.db');
db.pragma('journal_mode = WAL');
-- 4 таблицы + 2 индекса создаются при первом старте
CREATE INDEX IF NOT EXISTS idx_messages_chat ON messages (chat_id, id);
CREATE INDEX IF NOT EXISTS idx_participants_user ON chat_participants (user_id);
// Миграция: базам без last_read_at колонка добавится автоматически

📡 Socket.IO протокол

Подключение: io({ auth: { token } }). Клиент → сервер: join_chat(chatId). Сервер → клиент: new_message с полным объектом сообщения (включая sender_name и sender_avatar — JOIN уже сделан на сервере).

🧯 Ошибки — по-русски и по делу

«Заполните все поля», «Этот номер уже зарегистрирован», «Вы не в этом чате», «Файл слишком большой (максимум 10 МБ)». Глобальный обработчик multer-ошибок стоит после всех маршрутов — Express-стиль как по учебнику.

📏 Время — только ISO

Хелпер now() = new Date().toISOString() везде: пользователи, чаты, сообщения, отметки чтения. Сравнение дат в SQL работает строково и предсказуемо — без сюрпризов с часовыми поясами в сортировке.

✅ Что сделано правильно

  • Пароль никогда не возвращается клиенту (const {password: _pw, ...userInfo})
  • SQL — только подготовленные запросы db.prepare(…?): инъекциям негде жить
  • Загрузки: только image/*, ≤10 МБ, случайные имена файлов
  • Чужой чат недоступен ни для чтения, ни для записи (403, покрыто тестом)
  • Минимум 5 цифр в телефоне, непустые имя/сообщение/название группы

⚠️ Что честно стоит усилить

  • Задать свой JWT_SECRET в продакшене (README предупреждает!)
  • Добавить срок жизни токена (expiresIn) и refresh-схему
  • Rate-limit на /login против перебора паролей
  • HTTPS и httpOnly-куки вместо localStorage для токена
  • CORS origin:'*' у Socket.IO сузить до своего домена

🔢 Коды ответов системы

200 — успех · 400 — валидация/дубликат/неверный пароль · 401 — нет токена · 403 — токен битый или «вы не в этом чате» · 404 — пользователь не найден · 500 — ошибка базы (с логом в консоль сервера). Предсказуемый контракт для любого клиента.

Сверху вниз: константы → хелперы (now, normalizePhone) → схема БД + миграция → Express + multer → auth-middleware → 11 маршрутов → обработчик ошибок загрузки → Socket.IO с JWT-гейтом → Vite/dist → listen(3000, "0.0.0.0").

FAQ

Это настоящий мессенджер или макет?
Настоящий: регистрация, база SQLite, realtime через Socket.IO, загрузка фото на диск. Доказательство — scripts/e2e-test.mjs: 25 сквозных проверок против живого сервера, включая два одновременных сокет-подключения.
Почему SQLite, а не «взрослая» база?
Для сообщества и демо SQLite идеальна: ноль администрирования, один файл, WAL-режим, синхронный драйвер better-sqlite3 без пулов. Схема из 4 таблиц без боли переедет на PostgreSQL, когда вырастет нагрузка — SQL в проекте стандартный.
Почему весь бэкенд в одном файле на 443 строки?
Сознательный выбор: вся система видна целиком, деплой — одной командой, новичку легко читать сверху вниз. При росте файл естественно делится на модули auth/chats/socket — границы уже намечены комментариями разделов.
Как считаются непрочитанные сообщения?
У каждой пары (чат, пользователь) есть last_read_at. Непрочитанные = сообщения других пользователей новее этой отметки, один SQL-COUNT на чат. Открытие чата, ответ в нём или явный POST /read двигают отметку.
Что будет, если загрузить файл на 50 МБ или .exe?
Multer остановит загрузку на лимите 10 МБ и вернёт 400 «Файл слишком большой…», а не-картинку отклонит фильтр image/* с текстом «Можно загружать только изображения». Оба сценария понятны пользователю, второй покрыт тестом.
Можно ли поставить «Эко-культуру» в своём СНТ/школе?
Да: docker build + docker run -p 3000:3000 -v messenger-data:/data … — и у сообщества свой мессенджер на своём сервере. Не забудьте задать собственный JWT_SECRET и поставить HTTPS-прокси.
При чём тут турнир?
Эта презентация подготовлена для защиты проекта на турнире разработчиков: поэтому внутри — турнирная сетка технологий с аргументами «судей», честное сравнение с гигантами и все цифры, которые жюри может проверить по репозиторию. А в roadmap — конкурсы урожая: турнир переедет прямо в продукт 🍅🏆.
